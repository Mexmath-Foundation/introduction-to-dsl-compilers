# Step 1: three outputs from one model, as three loops

## What it shows
Lecture 9 ended with a model that passed every rule. This step does the three things the
syllabus calls *translation* with it, each as the most obvious loop:

| Function | Output | Who consumes it | The walk over the model |
|---|---|---|---|
| `to_dot` | text in the DOT language | Graphviz draws it | **down** the containment tree: every state once, every transition once, in document order |
| `run` | no text: a trace of states for a list of events | the user, or a test | **across** the references: from `initial`, follow `target` where the input says |
| `to_c` | text in C: an `enum` and a `switch` | a C compiler | **down** again, the same walk as `to_dot` with a different body |

Read the three functions side by side. Two of them have the same skeleton — `for s in
m.states: for t in s.transitions:` — and differ only in the line they emit. The third is
different in kind: it never enumerates the model; it keeps one variable, the current
state, and does one lookup per input event. The repeated skeleton is what the Visitor
pattern will package in step 2; the lookup loop is the interpreter of step 4.

Two decisions are visible in `run` and belong to the language, not to Python: an event the
machine never declared is an error in the *input* (`ValueError`, no file position — there
is no file to point at); a declared event with no transition in the current state is
ignored (the light stays where it is). Another language could stop, or log.

## Files
* [`fsm.tx`](fsm.tx) — the traffic-light grammar of Topic 5, `step-3-references`;
* [`light.fsm`](light.fsm) — the traffic light: `Red`, `Green`, `Yellow`, events `tick` and `panic`;
* [`three_loops.py`](three_loops.py) — `to_dot`, `run`, `to_c`, and a `main` that prints all three and writes `light.c`;
* [`main.c`](main.c) — a handwritten driver that feeds `TICK, TICK, PANIC, TICK, TICK, TICK` to the generated `step` function;
* [`light.c`](light.c) — generated by `three_loops.py`; committed so the C side can be built without Python.

## Run
```shell
uv run python topic-7/examples/step-1-three-loops/three_loops.py
```
Expected output:
```
=== to_dot
digraph Light {
  rankdir=LR;
  node [shape=circle];
  Red [shape=doublecircle];
  Red -> Green [label="tick"];
  Green -> Yellow [label="tick"];
  Green -> Red [label="panic"];
  Yellow -> Red [label="tick"];
}

=== run
['Red', 'Green', 'Yellow', 'Yellow', 'Red', 'Green', 'Yellow']
ValueError: unknown event 'boom'

=== to_c
enum state { RED, GREEN, YELLOW };
enum event { TICK, PANIC };

enum state step(enum state s, enum event e) {
  switch (s) {
  case RED:
    if (e == TICK) return GREEN;
    return s;
  ...
```
Draw the diagram (Graphviz must be installed, `dot -V`):
```shell
uv run python topic-7/examples/step-1-three-loops/three_loops.py | sed -n '/^digraph/,/^}/p' > light.dot
dot -Tpng light.dot -o light.png
```
Build and run the C program (any C compiler; shown with gcc):
```shell
cd topic-7/examples/step-1-three-loops
gcc light.c main.c -o light && ./light
```
It prints `0 1 2 2 0 1 2` — the same trace `run` printed, as enum indices (`Red = 0`,
`Green = 1`, `Yellow = 2`). Two translations of one model agreeing on one input: that is the
test step 5 turns into a script.
